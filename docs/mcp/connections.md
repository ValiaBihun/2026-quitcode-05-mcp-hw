# Підключення MCP-серверів LeadDesk (Task B)

- **Акаунти** (особисті, без клієнтських організацій і команд): Supabase — особистий акаунт на безплатному плані, одна
  особиста організація з одним порожнім проєктом (його `project_ref` є в `.mcp.json`; це не секрет) ·
  Vercel — особистий акаунт без команд, проєкт підключено до форка репозиторію через git-інтеграцію в дашборді
  (гілка `main`, налаштування за замовчуванням, без змінних оточення) · Figma — не використовували.
- **Третій сервер:** Playwright. Акаунт не потрібен і немає ліміту викликів (у Figma на плані Starter — 20 викликів на
  місяць на все), Chrome на машині вже є, а перевірка форми на `http://localhost:3000` показує живу поведінку
  застосунку. Спробувати Figma не було потреби.
- **Vercel CLI на цій машині:** у PATH `vercel` немає, глобально CLI не встановлювали. Під час кроку 5, коли MCP
  дав 403, агент запропонував CLI-фолбек, і користувачка його дозволила («так, дозволяю npx vercel»): агент один раз
  запустив CLI через `npx --yes vercel` (вхід через device flow) і отримав лог (`vercel inspect --logs`), а за її
  проханням («вийди з Vercel CLI») виконав `vercel logout`. Перевірено: файл з обліковими даними (`auth.json` у
  `com.vercel.cli`) після цього відсутній. Агент застеріг, що токен на боці Vercel міг лишитися чинним; чи відкликано
  його в Settings → Tokens, не зафіксовано. `vercel whoami` не запускали: CLI не залогінений, а встановлювати його
  заради цього не стали.

## Supabase: схема й сид

- Міграція `supabase/migrations/0001_leaddesk.sql` створює одну таблицю: `public.leads` (`id` у форматі `lead_NNNN`,
  `full_name`, `company`, `email`, `source`, `status` лише з п'яти значень `new`, `contacted`, `qualified`, `won`,
  `lost`, `budget`, `message`, `created_at`). Оператор `enable row level security` виконано без помилок; у Table Editor
  біля таблиці є кнопка «Add RLS policy».
- Сид `supabase/seed/leads.sql`: 20 рядків, `lead_0001`–`lead_0020`, ті самі, що в `materials/leads.json`. Перевірено
  запитом у SQL Editor дашборда: усього 20; за статусами new 6, contacted 4, qualified 3, won 5, lost 2; сума
  `budget` у won 9000; без `budget` 3 ліди; перший і останній `id` — `lead_0001` і `lead_0020`.
- Скільки інструментів Supabase видно з нашим URL: 9 (`apply_migration`, `execute_sql`, `generate_typescript_types`,
  `get_project_url`, `get_publishable_keys`, `list_extensions`, `list_migrations`, `list_tables`, `search_docs`).
- Виклики, якими створено схему й дані (за журналом сесії): `apply_migration` ×1 (`0001_leaddesk`; оператори
  збігаються з файлом, агент лише прибрав SQL-коментарі `--`); `execute_sql` ×2: один `insert` з усіма 20 рядками
  (агент сам об'єднав 20 insert-ів в один запит, усі значення дослівно збігаються з сидом) і `select count(*) from
  public.leads` (20). Відхилень немає. Сесія працювала в режимі `default` (запит на кожен виклик, їх немає в `allow`),
  «Always allow» не обирали (у `.claude/settings.local.json` немає правил). Самі кліки схвалення в журналі не
  фіксуються.

## Сесії: що вмикаємо разом

У кожній сесії — щонайбільше один сервер із правом запису; браузерний сервер — ніколи разом із Supabase. Час локальний
(UTC+3), дані — з журналів сесій і знімка `/mcp`.

| Крок | Увімкнено в `/mcp` | Сервер із правом запису в цій сесії |
|---|---|---|
| Міграція й сид (14:40, чат у застосунку Claude Code 2.1.288, режим `default`) | Project `supabase` (єдиний, до якого були виклики). У журналі сесії також згадуються project `vercel`, конектор claude.ai Supabase (без `project_ref`, 29 інструментів), вбудований браузер застосунку й Claude in Chrome. Playwright не підключився (таймаут). | `supabase` (`apply_migration`, `execute_sql`) |
| Лог білду (14:51–15:02, чат у застосунку, `default`) | Project `vercel` і конектор claude.ai Vercel (обидва дали 403 на `list_deployments`); також були доступні Supabase (project і конектор), Playwright, вбудований браузер, Claude in Chrome. | Bash (`npx vercel` за дозволом користувачки: вхід, `list`, `inspect --logs`, `logout`); записуючих викликів MCP немає |
| Знімок «до» (15:14, чат у застосунку) | Те саме, що в попередньому рядку; викликів інструментів немає. | — |
| Перша перевірка форми (15:38–15:45, CLI 2.1.296, `default`) | `playwright`, а також `supabase` і `vercel` (їх не вимкнули); викликів Supabase і Vercel не було. Замінена наступними рядками. | Bash (`npm run dev`) і Playwright (відправка форми) |
| Знімок «після» (близько 15:59, CLI, `default`) | Лише `playwright`; викликів інструментів немає. | — |
| Перевірка форми в браузері (16:39, CLI, `default`) | Лише `playwright`: на знімку `/mcp` увімкнено тільки його, у журналі немає Supabase, Vercel, Claude in Chrome і вбудованого браузера. | Playwright (відправка форми на `localhost`) |

- **Правило про браузер і Supabase порушено за конфігурацією в перших чотирьох рядках:** браузерні інструменти
  (вбудований браузер, Claude in Chrome або Playwright) були доступні в одній сесії з Supabase, а в перших трьох
  рядках — ще й конектор claude.ai Supabase без `project_ref`. За журналами жодного виклику браузерних інструментів чи
  цього конектора в сесіях із Supabase не було: усі три виклики Supabase пішли в project `supabase`. Виправили те, що
  можна було виправити: перевірку форми повторили в чистій сесії (останній рядок), знімок «після» теж зроблено в чистій.
  Міграцію й лог білду вже не повторити.
- **Додаткові спроби, не враховані вище:** чат у застосунку, де перелік 21 інструмента Playwright запитали ще до
  чистого знімка; і чат у застосунку, де запит про форму помилково пішов у вбудований браузер, а не в Playwright (одна
  навігація на `localhost:3000`).
- **Конектори claude.ai з'являються в сесіях без запиту** (Supabase на 29 інструментів, Vercel на 238, Claude in
  Chrome): їх треба вимикати в `/mcp` окремо. У чистих сесіях вони вимкнені.

  завдяки `--no-webmcp`.
